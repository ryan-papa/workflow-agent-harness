# Harness: PRD 단계

## 구체화 (Claude)

- **추론 우선:** 유추 가능 항목은 가정 명시, 유추 불가 결정만 질문 → [`skills/rp-specify.md`](skills/rp-specify.md) "추론 우선 판정"
- 질문 1개씩 대화형 진행
- 기술 스택·구현 방식 불명확 시 자동 리서치
- **종료 조건:** 5단계 항목 확정(질문 또는 추론 가정) + 후속 항목 수집 + 구현 조건 검증 완료 시 자동 종료
- **구체화 리트머스:** 서로 다른 두 사람이 이 문서만 보고 작업했을 때 같은 방향을 향하는가?

**구체화 5단계 + 후속 항목:**

| 단계 | 묻는 것 | 대표 질문 |
|:----:|---------|----------|
| 1. 존재 이유 | 왜, 지금 왜 | "지금 이게 없어서 어떤 일이 안 풀리고 있나?" |
| 2. 사용자 | 누가 | "가장 자주 쓸 사람 한 명을 상황으로 묘사해주세요" |
| 3. 핵심 장면 | 무엇을, 어떻게 | "가장 자주 일어날 장면 3개를 순서대로요" |
| 4. 경계 | 무엇이 아닌가 | "'이런 느낌은 아니다' 싶은 레퍼런스가 있나?" |
| 5. 성공 기준 | 어떻게 알까 | "3개월 뒤 어떤 숫자/장면을 보면 성공? 반대로 접을 기준은?" |

**각 항목이 가져야 할 4가지 성질:**

| 성질 | 설명 |
|------|------|
| 관찰 가능 | 근거가 있다 |
| 반증 가능 | 확인할 방법이 있다 |
| 경계가 있다 | 포함/비포함이 분명하다 |
| 분기가 있다 | 예외·에러·빈 상태가 고려되어 있다 |

**후속 항목:**

1. 화면·기능 구체화:

| 항목 | 질문 |
|------|------|
| 화면 목록 | 필요한 화면은 몇 개인가 |
| 화면별 정보 | 어떤 정보를 어떤 형태(카드/리스트/지도/그래프)로 보여줄 것인가 |
| 입력·출력 | 사용자가 무엇을 입력하고, 무엇을 보는가 |
| 탐색 방식 | 사용자가 원하는 정보에 도달하는 경로는 (검색/필터/지도/추천 등) |
| 정렬·필터 | 정보를 어떤 기준으로 정렬·필터링하는가 |
| 데이터 소스 | 핵심 데이터를 어디서 확보하는가 (API/UGC/크롤링/직접 입력) |
| 추천·처리 로직 | 데이터를 어떤 기준으로 가공·추천하는가 (평점/개인화/트렌드 등) |
| 빈 상태·에러 | 결과 없음, 오류, 로딩 시 어떻게 보여주는가 |
| 디자인 톤 | 분위기, 컬러, 참고 사이트 |

2. 시장 조사:
   - 유사 서비스 검색 + 기능/화면/철학 분석
   - 차별점 도출 → 재구체화에 반영

3. 기술 정보:

| 항목 | 예시 |
|------|------|
| 개발 언어·런타임 | Python, Node.js 등 |
| 실행 환경 | 로컬, 클라우드 등 |
| 외부 연동 | API, 메시지 채널 등 |
| 인증·인가 | 로그인 방식, 토큰 발급 |

**판정 순서:** 존재 이유 → 사용자 → 핵심 장면 → 경계 → 성공 기준 → 화면·기능 구체화 → 시장 조사 → 기술 정보

## PRD 작성 (Doc Agent)

**섹션:**

| 섹션 | 내용 |
|------|------|
| 개요·목적 | 배경, 목표, 범위 |
| 사용자 스토리 | `As a ... I want ... So that ...` |
| 기능 요구사항 | 구체적 동작 정의 |
| 비기능 요구사항 | 성능, 보안, 확장성 |
| 제약사항 | 기술·비즈니스 제약 |
| Open Issues | TBD 항목 추적 |

**파일명:**
```
repositories/[project]/docs/prd/YYYYMMDD_HHMMSS_[feature]_[8자리랜덤].md
```
- `YYYYMMDD_HHMMSS`: `date +%Y%m%d_%H%M%S` 실행값
- 랜덤 문자열: 세션 시작 시 1회 생성 후 유지

### 간소 PRD (하네스 메타 변경용)

하네스 자체 문서(`docs/`, `CLAUDE.md`, 스킬, `.claude/settings.json`) 변경은 **간소 PRD** 허용 (완전 생략 금지).

| 필수 섹션 | 내용 |
|---------|------|
| 변경 이유 | 왜 이 메타 변경이 필요한가 |
| 영향 파일 | 변경되는 파일 목록과 역할 |
| 롤백 전략 | 문제 발생 시 원복 방법 |
| 검증 | CI·서브에이전트 리뷰 |

**파일명:** `docs/prd/[feature]/prd.md` (하네스 루트 기준)

## PRD 리뷰 (Full flow 2관점 병렬 실행)

```
Doc Agent 작성 완료
  ↓
┌─────────────────────────────┬─────────────────────────────┐
│ [4] 기획 리뷰                │ [5] 엔지니어링 리뷰           │
│ Planning Review Sub-Agent    │ Engineering Review Sub-Agent │
│ (메인 런타임의 서브에이전트)   │ (메인 런타임의 서브에이전트)    │
└─────────────────────────────┴─────────────────────────────┘
  ↓ 동일 메시지에서 동시 발사, 컨텍스트 미공유 독립 판정
양축 통과 (각 평균 ≥ 8.0 + 각 항목 ≥ 7)
  ↓
다음 단계 자동 진입
```

한 축만 미달이면 **미달 축만 재실행**(축별 독립 카운터 3회). 수정이 상대 관점 영역을 건드리거나 PRD 전면 개작 시 통과한 축도 재검증 — SSOT: [`harness-absolute-rules.md`](harness-absolute-rules.md) "리뷰 단계 = 관점 분리".

**⛔ 실행 주체**: 각 리뷰 단계는 **반드시 메인 런타임의 서브에이전트(Claude-Lead=Agent 툴 / Codex-Lead=`spawn_agent`)** 가 수행한다. 메인 에이전트의 셀프 채점 금지. SSOT: [`harness-absolute-rules.md`](harness-absolute-rules.md) "작성 모드 및 리뷰 매트릭스".

Lite track은 [`harness-workflow.md`](harness-workflow.md) 의 간이 PRD + 통합 plan/engineering 리뷰 예외를 따른다.

각 단계 미달 시 Doc Agent 재작성, 최대 3회 반복 (매 회차 새 서브에이전트). **3회 미달 시 자동 중단 + 사용자 결정 요청** (강행/재설계/중단).

---

### 1단계: 기획 리뷰

→ 평가 항목 9개 SSOT: [`skills/rp-plan-review.md`](skills/rp-plan-review.md) "평가 항목" 표

### 2단계: 엔지니어링 리뷰

→ 평가 항목 5개 SSOT: [`skills/rp-eng-review.md`](skills/rp-eng-review.md) "평가 항목" 표
**리뷰 원칙:** 각 항목에 "이걸 어떻게 테스트할 수 있는가?" 질문 적용

---

### 공통 규칙

**판정 (두 리뷰 모두 동일):**
- 평균 ≥ 8.0 **+ 각 항목 ≥ 7** → 통과
- 평균 < 8.0 또는 항목별 최저 < 7 → Doc Agent가 PRD 본문 갱신 후 재실행 (인-메모리 최대 3회)
- 3회 후 미달 → `Max retry reached`, 사용자 판단

**결과 기록:** 별도 파일·점수표 보존 없음. 리뷰 지적은 PRD 본문 자체에 반영. 최종 PRD가 단일 결과물.

**규칙:** 작성·리뷰·개선은 자동 진행. 최종 문서만 사용자에게 전달.

## PRD 상태

| 상태 | 조건 |
|------|------|
| `Draft` | 최초 작성 |
| `In Review` | [4]·[5] 병렬 리뷰 진행 중 |
| `Partial Pass` | 한 축만 통과 — 미달 축 재실행 중 |
| `Approved` | 두 축 모두 통과 → 바로 개발 진입 |
| `Max retry reached` | 축별 3회 후 미달 |
